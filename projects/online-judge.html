Online judge

A programming-judge project in its early backend stage. The part that exists is a Bun/TypeScript API and a careful PostgreSQL model for users, versioned problems, and submissions. The web app and the code-running worker still need to be built.

Current status / checked against the repository

The API, authentication endpoints, problem create/read routes, Drizzle schema, migration, seed file, and shared TypeScript contracts exist. The packages/web package has no app source, packages/judge-worker has only a package manifest, and problem search is an empty handler. There is no submission API or execution path in this checkout.

I am keeping this page in two layers: implemented now and the architecture I want to build next. That distinction matters most here because an enum named RUNNING and a Docker Compose service do not mean user code is currently being run.

Implemented system map

This is the request path that can be traced through the current code: a client would call the Express API, auth middleware reads a JWT from a cookie, controllers call services, and Drizzle reads or writes PostgreSQL. The diagram intentionally leaves the browser and judge worker marked as missing.

The schema is the strongest part so far

The database splits a problem's stable identity from its editable content. problems holds a unique slug, owner, visibility, and status. problem_versions holds the statement, limits, difficulty, checker settings, and test-case object key. submissions references both the stable problem and the exact version it was judged against.

One transactionProblem creation inserts the identity row and version 1 in one transaction, so a failure does not leave a shell without content.
Typed query layerDrizzle is initialized with the schema and Postgres client. TypeScript types are inferred from the same table definitions.

Why pin a submission to a version?

Suppose a problem's hidden tests change next week. If an old submission only points at the problem slug, it becomes hard to answer a basic question: “What exact statement, limits, and test set did this verdict use?” A version row makes that context explicit. A submission keeps both problemId and problemVersionId, and the version carries its own test-case key and version.

The worker contract is sketched, not connected

packages/shared defines supported-language configuration, checker types, verdict strings, valid state transitions, topic names, and typed submission-created/judged event shapes. That is a useful boundary: API and worker can agree on a message format without duplicating string literals. At the moment, no producer or consumer imports these contracts into a running judge path. There are also a couple of contract mismatches to fix before connecting them: the database uses UUIDs for problem-version IDs while the submission event types those IDs as numbers, and the event config calls the checker key checkerCustomScriptS3Key while the schema uses checkerScriptS3Key.

Target judging pipeline: the next architecture

This is the system I would build around the existing tables and event types. It is a design sketch, not a description of current behavior. The API should accept source, pin an immutable problem version, store the source and submission metadata, and publish an event. A worker should claim a job, fetch only the versioned tests, compile and run inside a hardened isolation boundary, then persist a verdict. The client can poll or subscribe to status changes.

Isolation is a security boundary, not a Docker checkbox

Executing user code safely takes more than a container: privilege separation, syscall restrictions, CPU/memory/process/output/time limits, filesystem policy, network policy, cleanup, and host hardening all need deliberate treatment. The current repo has no runner, so it would be misleading to claim any of these controls are in place.

Gaps I would close before calling this a judge

  • Public problem response. The read service currently loads full problem-version rows. Before using this as a public endpoint, return an explicit safe projection: hidden test-case keys and checker-script keys should never be serialized to a learner. Define access rules for draft, review, archived, and published problems.
  • Authorization roles. Problem creation authenticates a user but the current handler does not check that the account is an administrator or permitted author. Add role/ownership policy at the service boundary.
  • Search and submissions. The search handler is empty; there are no submission controllers/routes, code storage upload, queue producer, worker consumer, or result stream.
  • Worker boundary. Specify supported language images, isolation, resource enforcement, output truncation, cleanup, and failure recovery before running arbitrary code.
  • Event reliability and contract consistency. Align ID and field names between SQL rows and TypeScript events, then decide how the API avoids a saved submission with a missing queue event, how workers deduplicate, and how retries avoid overwriting a newer verdict. The shared types are a starting contract, not the solution.
  • Web application. The package is present, but there are no interface components in the checked-in folder yet.

What I want to build next

  1. Finish safe problem read models and role-aware create/read policies.
  2. Implement paginated problem search and a submission API that pins a version.
  3. Store source code out of the database while keeping a stable object key and checksum.
  4. Connect the API to the broker with idempotent event IDs and an outbox strategy.
  5. Build a small worker prototype around one language, then test the isolation boundary separately from the product API.
  6. Add a minimal web client only after the API contracts stop moving.

That order is intentionally unglamorous. The UI is the visible part of an online judge, but correctness depends on the quieter parts: which version was judged, whether a job ran once, what an accepted result means, and how hostile code is kept away from the rest of the system.

Where to look in the repository

  • packages/api/src/db/schema.ts — users, problems, problem versions, submissions, constraints
  • packages/api/src/services/problem.services.ts — transactional create and problem reads
  • packages/api/src/controllers/problem.controllers.ts — handlers, including the unfinished search handler
  • packages/shared/src/events.ts — event envelopes and topic names
  • packages/shared/src/verdicts.ts — verdict vocabulary and legal state transitions
