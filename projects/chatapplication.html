Project 01 / Real-time messaging

ChatApplication

A one-to-one chat app where the interesting part is not the bubble. It is deciding what “sent”, “delivered”, and “seen” mean—and making those labels agree with what the server actually knows.

The project is a private, one-to-one messenger. It has Google sign-in, user discovery, a chat-request gate, message history, image messages, replies, edits, reactions, typing indicators, presence, delivery and seen receipts, and blocking. The React client uses HTTP for account and history operations; a ws connection carries live events.

The central design choice is simple: the socket makes changes feel immediate, while MongoDB remains the place to recover the conversation after a refresh or disconnect. Those are different jobs, so they get different paths.

System map: two paths, one source of truth

This is a data-flow view of the implementation. Solid arrows are HTTP/database work; the dotted arrows are live events. The recipient does not need to be online for the sender's message to be saved.

A message's trip, step by step

The client sends a normal authenticated POST /send/:receiverId. The API checks that the two people have an accepted chat, rejects blocked pairs, validates a reply belongs to that chat, and only then accepts the message. For an image, it validates the upload and sends the bytes to Cloudinary. The service creates the Mongo document, updates the chat's last-message pointer, populates the response shape, and pushes the new message to the recipient's open socket.

Status labels need evidence

The stored message has a state and timestamps. A newly created message defaults to sent. When the recipient's socket handles it, the client emits message:delivered; the server checks that this user is the receiver before changing the row. Opening a conversation sends message:seen-instant or a late-seen batch. When the receiver reconnects, the server also marks their pending incoming messages delivered and notifies each sender.

A useful boundary

The server writes a message before it pushes it. But saving the message and updating the chat pointer are two separate database operations, and pushing the socket event is another step. A production-grade version would make the durable changes atomic and use an outbox or another retryable event mechanism for reliable fan-out.

Chat requests prevent unsolicited conversations

Creating a chat request makes a Chat with status: pending and an initiator, then records a system message. The receiver can accept or decline. Only the other member—not the initiator—can make that decision. Accepting creates a system message and conditionally updates a still-pending chat. A partial unique index on the sorted member pair prevents multiple active pending/accepted chats between the same two users.

The schema follows the conversation

Messages are their own collection rather than an unbounded array inside a chat. That lets history be fetched in pages, keeps each message addressable for edits/reactions/receipts, and gives the query a compound index on chatId and descending createdAt. The chat keeps a reference to its latest message for the conversation list.

Security and failure paths

  • Authentication. Google ID tokens are verified server-side. A JWT session token is stored in the user's session list and sent in an HTTP-only cookie. The WebSocket checks the request origin, parses that cookie, verifies the JWT, and confirms the session still exists and has not expired.
  • Authorization. Message validation requires an accepted chat between the pair, checks blocking in both directions, and checks that a reply target belongs to that chat. Receipt updates match the authenticated receiver, rather than trusting a client-supplied receiver ID.
  • Uploads. Multer accepts image files into memory; server-side file-type validation runs before Cloudinary upload. The message stores the Cloudinary URL and metadata, not the image bytes.
  • Socket limits. The WebSocket server sets a 64 KiB maximum payload and rejects missing/invalid sessions or unapproved origins at connection time.
  • Live state is local. Online-user and watcher maps are in process memory. They work in one server process; running multiple API instances would need shared presence/fan-out and a consistent connection strategy.

For conversation history, the API validates a date cursor and caps the page limit at 100. A stronger cursor for heavy concurrent traffic could combine createdAt with the message ID, so two rows with the same timestamp cannot create a gap between pages.

What I learned building it

“Real time” is not the same as “reliable.” A socket can disappear after the database write and before the recipient sees the event. Storing first makes the message recoverable, but it does not guarantee that every live notification is delivered exactly once. That guarantee needs a durable event handoff, retry, and idempotent client handling.

I also learned to make state names earn their keep. The UI's double checkmarks should correspond to server-verified events, not merely to a call to send() from the sender's browser. This project has separate status events and timestamps, which gives that distinction a place in both code and data.

Honest scope

This repository contains the application and focused frontend/backend tests. The write-up describes the code found in the project folders; it does not claim horizontal scaling, exactly-once event delivery, or a production deployment.
