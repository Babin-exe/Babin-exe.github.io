What the WebSocket handshake does (and doesn't)

A WebSocket connection begins as an HTTP request. The upgrade proves that both endpoints agreed to switch protocols; it does not encrypt the connection, authenticate the user, or make your event payloads safe.

HTTP is a request/response protocol. A browser asks for a resource; the server sends a response. WebSocket keeps a connection open so either side can send a frame whenever it has an event. The standard does not start with a brand-new transport: it asks the server to switch the existing HTTP connection.

The upgrade request is still HTTP

A browser request contains an upgrade intent, a version, and a fresh random key. In an HTTP/1.1 sketch, it looks roughly like this:

GET /live HTTP/1.1
Host: chat.example
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://chat.example

If the server accepts, it replies with 101 Switching Protocols and the matching Upgrade headers. After that response, both ends exchange WebSocket frames instead of ordinary HTTP message bodies on that connection.

The key calculation is a protocol check, not a secret

The server computes Sec-WebSocket-Accept from the client's key plus a fixed GUID, hashes that value with SHA-1, then Base64-encodes the digest. The client can compute the same answer and verify the server understood the WebSocket handshake.

accept = Base64(SHA1(clientKey + websocketGuid))

The client key is public in the request; it is not a password. The accept value prevents a server from mistakenly treating a non-WebSocket HTTP endpoint as an upgraded socket. It is not encryption, not authentication, and not authorization. Use wss:// for TLS encryption, and authenticate the user separately.

After upgrade, it is frames—not raw JSON strings

WebSocket frames have a header, a payload length, and optional masking. The base header contains a final-frame bit, reserved bits for negotiated extensions, an opcode, a mask bit, and a payload length. Text and binary messages may be fragmented into multiple frames; control frames such as ping, pong, and close have special rules. A browser client masks frames it sends to the server; a server does not mask its frames.

What the handshake cannot do for you

  • It does not authenticate. A WebSocket is still an application connection. Check a signed session/token on connect and authorize every action.
  • It does not make the origin trustworthy. Browsers send an Origin header. Validate it against an explicit allow-list, especially when cookies authenticate the socket, to reduce cross-site WebSocket hijacking risk.
  • It does not encrypt. Use wss:// so the transport is protected by TLS. The accept hash is not a security secret.
  • It does not validate events. Limit payload size, parse safely, validate message types and fields, and verify the user may act on the target conversation or message.
  • It does not make delivery durable. If a connection closes, a frame that was in flight may be lost from the client's perspective. Persist state and provide a catch-up path.

Liveness needs a deadline and a recovery path

TCP may remain open while one side is no longer useful. Ping/pong control frames help endpoints notice a dead peer. The browser's WebSocket API handles protocol-level ping/pong without exposing a method to send a control ping from JavaScript, so applications sometimes add their own JSON heartbeat as well.

In ChatApplication, the server sends a protocol ping about every 30 seconds and marks the connection dead if the previous ping did not receive a pong. The client also sends an application-level ping after about 40 seconds without a server event; the server replies with JSON pong, and the client closes a quiet connection after the next check at roughly 45 seconds. The frontend reconnects after closure and refreshes online state. The two heartbeat mechanisms are separate; changing one requires checking the other.

How this fits the chat project

The backend creates a WebSocketServer on the same HTTP server. At connection time, it checks Origin, reads the session cookie, verifies the JWT, and confirms that token is still in the user's session list. It keeps sockets in a per-user map, then emits typed JSON events for new messages, presence, typing, chat requests, reactions, edits, and receipts. The service persists messages through REST before it pushes a new-message event.

This is why a raw WebSocket library is enough for the current project: it owns its event format, reconnection, and presence rules. A higher-level library can add rooms, fallbacks, acknowledgements, and reconnection helpers, but those are product choices. They do not remove the need to define what each event means or how it recovers after a disconnect.

A practical reading rule

When you see “WebSocket is connected,” read that as “there is a transport right now.” Ask separate questions for identity, permission, persistence, acknowledgement, and replay.
