A chat message is more than a socket event

A WebSocket can move a message quickly. It cannot prove that the message was saved, received, or read. Those are separate claims, and each one needs a separate piece of evidence.

In the ChatApplication repository, the sender does not send message content over WebSocket. The browser posts to an authenticated Express route. The API checks the conversation, saves the message in MongoDB, updates the chat's last-message pointer, then sends a live message event to the recipient if that user has a connected socket. This is a useful separation: HTTP gives the sender a response; the socket makes the receiver's screen update without polling.

Four different facts often get collapsed into one

A successful socket send alone proves none of the receiver-side steps.

The socket library's send() call only puts bytes onto a connection. It does not mean the remote UI rendered them, that the person looked at them, or that the receiving browser still has the event after a crash. A status name should describe the strongest evidence the server has—not the most optimistic interpretation.

The path in this project

Before the write, the service verifies an accepted chat exists between sender and receiver, checks the block relation, validates text or image requirements, and verifies a reply target belongs to the same chat. The message document carries sender, receiver, chat, content/type, optional image metadata, reply reference, reactions, status, and delivery/seen timestamps.

The state machine is small, but semantics matter

On connection, the server finds messages addressed to that user that remain sent, marks them delivered, and informs their senders. On opening a conversation, the client emits a “seen late” event for pending messages from that contact. If a new message arrives while its chat is open, the client emits an immediate seen event. Both paths let the receiver's identity come from the authenticated socket rather than trusting a user ID in the payload.

Offline does not mean lost—but the socket is not a queue

If the receiver has no live connection, the API still stores the message. sendToUser simply has no socket set to write to. When that account connects again, the server reconciles pending delivery status. The frontend also reconnects after a close and fetches history over HTTP when a conversation is opened.

Seen event is repeatedMessage is already seen.Handlers avoid changing an already-seen message in instant path.

“Exactly once” is usually the wrong promise for a networked system. A client can retry after an unknown outcome; a worker or gateway can deliver twice; a response can vanish after a commit. A more practical design is at-least-once delivery plus stable message IDs and idempotent updates, so duplicate events do not create duplicate messages or rewind status.

A stronger version of this design

The useful lesson from this codebase is not “always add a queue.” It is to name each guarantee, trace the evidence that supports it, and add machinery only when the gap matters. For a small messenger, persisted history and reconnect sync are a reasonable foundation. For multi-instance scale or stronger delivery guarantees, process-local sockets and direct best-effort pushes are not enough.
