The DAO hack: one callback too early

The 2016 DAO exploit is a useful case study because the failure was not a broken hash or a stolen key. A contract gave control to another contract before updating its own accounting—and the callback came back in while the old balance was still visible.

In 2016, The DAO was a large Ethereum-based investment organization whose contract let participants withdraw their share by “splitting” into a child DAO. On June 17, the Ethereum Foundation described an active exploit: the attacker called the split operation and recursively called it again from inside that operation, collecting Ether multiple times in one transaction. More than 3.6 million ETH was moved into a child DAO. The child DAO's waiting period meant that the funds were not immediately withdrawable. The Foundation's incident update describes the recursion; EIP-779 records the later fork's state change.

A distinction worth keeping

This was a vulnerability in a particular smart contract and its interaction logic. It was not a break of Ethereum's cryptographic signatures or consensus protocol. The chain executed the contract's code; the design mistake was in what that code allowed callers to do.

The context: “withdraw my share” crosses a trust boundary

A contract can call another contract. That call is not a passive transfer of bytes: the receiving contract can run code before the original call returns. If the original contract has not finished updating its own state, the receiver can call back into it while its accounting is halfway through a withdrawal.

The simplified example below is not The DAO's source code. It only shows the dangerous ordering in generic withdrawal logic: calculate a payout, make an external call, then reduce the recorded balance.

// Unsafe ordering (simplified)
function withdraw() {
    amount = credit[msg.sender];
    sendEther(msg.sender, amount);  // recipient code may run here
    credit[msg.sender] = 0;         // too late if callback re-enters
}

If the recipient is a contract, the payment call can trigger its fallback/receive code. If that code calls withdraw() again, the outer invocation has not yet set the credit to zero. The nested invocation sees the same entitlement and performs another payment. The bug is a control-flow issue: execution leaves the contract before its state has reached a safe point.

The reentrant call, one stack frame at a time

The DAO's split path was the vulnerable operation. It could call into the destination DAO while the original split/accounting path was still active; the recursive call reused state that had not yet been fully updated. The exploit drained value into a child DAO under the contract's split mechanism, rather than reversing blocks or forging transactions.

The fix starts with ordering

The standard Checks–Effects–Interactions pattern is a useful first defense:

  1. Checks: verify caller, arguments, and available balance.
  2. Effects: update internal accounting so the entitlement is consumed.
  3. Interactions: only then call an external contract or transfer value.
// Safer ordering (simplified; not production code)
function withdraw() {
    amount = credit[msg.sender];
    require(amount > 0);
    credit[msg.sender] = 0;         // effect first
    sendEther(msg.sender, amount);  // interaction last
}

Other defenses include pull payments, where a recipient withdraws separately, and a reentrancy guard that prevents nested entry into sensitive functions. These help, but neither replaces understanding which state must change and which functions share that state. Reentrancy can cross function boundaries or involve a chain of contracts, not just recurse into the same line of code.

Do not rely on a tiny gas stipend

Modern smart-contract guidance recommends ordering state updates before external calls and using explicit guards where appropriate. A fixed gas stipend is not a complete security model; opcode pricing and call behavior can change, and external calls remain a control-transfer boundary.

The community response: a contentious fork

The response became a governance question as much as a technical one. The Foundation initially proposed a software fork that would prevent withdrawals from The DAO and its child DAOs during the lock period; the June 17 statement explicitly said that this was not a rollback of blocks. After debate and a vote, the hard fork activated at block 1,920,000 on July 20, 2016. EIP-779 describes it as an “irregular state change”: balances from a specified set of DAO-related accounts moved to a recovery contract where token holders could withdraw.

The hard fork was controversial precisely because the technology question (“what does this bytecode do?”) and the governance question (“should the community intervene?”) were different questions. Ethereum Classic continued on the non-fork chain. The incident became a lasting reminder that immutable execution does not remove social choices; it makes those choices visible and costly. The Foundation's fork completion notice records the movement at block 1,920,000, while the current Solidity security guidance explains Checks–Effects–Interactions.

What still applies to contract design

  • Model external calls as control transfers. Any recipient code may run before the caller resumes.
  • Write invariants down. “A claim can be paid at most once” is clearer than “withdraw should work.”
  • Update state before interaction. Use Checks–Effects–Interactions and consider a guard for shared mutable state.
  • Use adversarial tests. Make a receiver contract that re-enters, reverts, consumes gas, and makes nested calls.
  • Keep the response plan in mind. Upgradeability, pause authority, governance, and recovery paths are protocol choices, not afterthoughts.
  • Separate a contract exploit from a chain exploit. In this case, the EVM ran the contract as programmed; the vulnerability was the contract's state-transition design.

The DAO incident matters because a small ordering mistake sat at the intersection of code, money, and governance. The mechanics fit in a short call graph. The consequences did not.
