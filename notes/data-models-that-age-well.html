Data models that can survive a change of mind

A schema is a record of the questions an application needs to answer. Chat history and problem versions ask different questions, so the projects use different shapes—and both rely on constraints to keep the answers trustworthy.

A common way to start modeling is to ask “what objects are in the app?” I find it more useful to ask “what questions does the app need to answer, and what must remain true when it answers them?” A chat app needs to fetch a conversation's recent messages. A judge needs to explain which exact problem tests produced a submission's verdict. The models that follow from those queries are not interchangeable.

Begin from the access patterns

The useful default is to model for real operations, then let constraints protect invariants. An index is not decoration; it is a commitment to make one access pattern affordable. A unique constraint is stronger than “we checked the value first,” because another request can race the check.

Chat data: keep the growing timeline outside the chat row

The ChatApplication has separate User, Chat, Message, and Block models. A chat keeps the member references, initiator, request status, and a reference to its last message. Each message is a separate document with a chat ID, sender and receiver IDs, content/type, delivery state, optional reply reference, image metadata, and reactions. The history can grow without turning one chat document into an ever-expanding array.

Index sketch
chatId = ?
createdAt < cursor
ORDER BY createdAt DESC

Equality filter first, then the sort key. The actual Mongo index is { chatId: 1, createdAt: -1 }.

One small but deliberate detail: before save, the chat sorts member IDs and joins them into memberKey. A partial unique index on that key applies to pending and accepted chats. Sorting means the same pair, in either order, maps to the same key. The message index on { chatId: 1, createdAt: -1 } matches the recent-history query.

There is a modeling trade-off here: the members array is convenient for a two-person lookup, but the database schema does not itself enforce “exactly two members.” That invariant currently lives in how the application constructs chats. If group chats arrive later, some assumptions in the request and presence logic will need revisiting.

Problem versions: preserve the context of an old result

The judge schema is relational. problems records identity and publication state. Each row in problem_versions stores the statement and execution limits for that revision. A submission points to the problem and version that it belongs to, plus source-code key, language, verdict, resource measurements, and runner output fields.

Both projects use constraints to encode rules close to the data. The judge schema checks, for example, that version numbers are positive, difficulty and resource limits fall in configured ranges, and STANDARD checkers do not have a checker script while SPECIAL/INTERACTIVE checkers do. Its problem service writes the identity and first version in a transaction.

An index is a promise about a query

Indexes are useful when they line up with filters and ordering. The ChatApplication asks for a page of messages from one chat, sorted newest first, so chatId followed by createdAt descending is a sensible access path. The user collection has indexes for verified users and normalized search fields. The judge adds unique indexes for usernames, emails, problem slugs, and the version-number pair.

Constraints and transactions solve different problems

A unique index protects an invariant even if two requests race. A transaction groups multiple database writes so they commit or roll back together. The judge's initial problem creation uses a transaction for the problem row and version 1. The ChatApplication message path currently writes the message and updates Chat.lastMessage as separate operations; that is a reasonable place to consider a transaction if stale previews become a correctness issue.

Pagination is part of the data contract

Chat history sorts newest first, applies an optional date cursor, limits a page, then reverses the results for display. That is much better than loading every message. A timestamp-only cursor can be ambiguous if several messages share the same timestamp boundary. A more stable keyset cursor includes both sort fields, such as (createdAt, _id), with a matching compound index and tie-break condition.

For the online judge, version pinning does a similar job in a different way: it makes a historical result point to the exact input definition that gave the result meaning. Good data design is often about preserving context as much as storing the newest value.

A short checklist I use now

  1. Write down the top read/write questions before choosing document shapes or joins.
  2. Make every “must never happen” rule a database constraint where possible, and validate at the API boundary for useful errors.
  3. Index the filter and sort together; keep indexes that earn their write/storage cost.
  4. Use a transaction when several writes describe one indivisible change.
  5. Store a version or snapshot when future edits should not rewrite the meaning of old records.
  6. Paginate with a deterministic cursor and test the boundary cases (equal timestamps, inserts between pages).
  7. Return explicit safe projections. A field existing in the schema does not mean it belongs in every API response.
