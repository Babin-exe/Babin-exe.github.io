An online judge is a pipeline, not a button

“Run this code” sounds like one operation. A real judge has to accept an untrusted program, pin the exact problem version, execute safely, measure it, and make sure its verdict survives retries and failures.

Current project status

The repository defines users, problems, problem versions, submissions, language configs, verdicts, and event payloads. Its local Compose file lists Postgres, Redis, Redpanda, and MinIO. The web client, submission endpoint, broker integration, object upload, and judge worker are not implemented in this checkout. Everything in this note beyond those foundations is a proposed design, not shipped behavior.

That distinction is part of the lesson. Configuration is not a running feature; a state name is not a transition that actually happens. Before thinking about a queue or a sandbox, make the data and failure semantics explicit.

The full job path

A submission should become a durable, version-pinned job before any worker executes it. A practical sequence: authenticate and validate; resolve the published problem version; store source and metadata; create a PENDING record; publish a job event; let a worker claim it; compile and run in an isolated environment; save measurements and a terminal verdict; make that result visible to the user.

Verdicts form a state machine

The shared package declares transitions such as PENDING → COMPILING → RUNNING → ACCEPTED. Other terminal outcomes include compilation error, wrong answer, time limit, memory limit, runtime error, internal error, and cancellation. A worker should only apply a transition if it is valid for the current state and for the current attempt.

Why model these transitions rather than store an arbitrary string? It prevents impossible jumps, makes the UI predictable, and gives retry logic a vocabulary. The next concern is attempts: if a job is rejudged while an old worker is slow, a late result from the old attempt must not overwrite the new one. A monotonically increasing attempt number or unique execution ID can make that check explicit.

The sandbox is several boundaries, not one box

Submitted code is adversarial input. It may loop forever, use too much memory, fork children, flood output, inspect files, probe the network, exploit a compiler/runtime bug, or try to reach the host. A container shares the host kernel, so “put it in Docker” is not a complete security argument.

Limits must measure the thing they claim to limit

A judge usually needs both an execution deadline and resource limits. They are not interchangeable:

LimitProtects againstWhat to track
Wall-clock timeoutBlocked I/O, sleeping, deadlock, slow external waits.Elapsed time from supervisor start to completion.
CPU budgetCompute loops and expensive work.Actual CPU time, plus scheduler throttling where needed.
MemoryAllocation blowups and runaway processes.Memory cgroup use and OOM outcome.
Process countFork bombs / child-process explosion.PID controller count and termination behavior.
Output sizeDisk or pipe exhaustion from huge stdout/stderr.Bytes read; stop or truncate when cap is crossed.
Compile timePathological compiler work.A separate compile deadline and output cap.

One subtle cgroups detail: with cgroup v2, cpu.max is written as MAX PERIOD in microseconds. For example, 200000 100000 means up to 200,000 μs of CPU time in each 100,000 μs period—roughly two CPUs of bandwidth while the quota is available. It is not “allow this job two seconds of total CPU.” A total per-submission CPU-time budget needs usage accounting and a supervisor that stops the process when the accumulated usage crosses the chosen threshold.

Filesystem flags need the same precision. A tmpfs mounted with noexec prevents binaries from being executed from that mount. If a C++ compile writes its output binary into that workspace and then runs it there, that policy contradicts the run step. You can separate source and executable locations, compile in a controlled location with an explicit policy, or choose a different execution design—but the mount options and pipeline must agree.

Small but important

Docker documents that a tmpfs mount's contents count toward the container's memory cgroup. A 64 MiB work mount does not add 64 MiB outside the memory limit. It consumes part of the budget.

A queue gives control, then asks for careful failure handling

A broker decouples the fast API request from slower execution. It also creates new questions: did the API save the row but fail to publish? Can a worker crash after claiming the message? What if it finishes the program but dies before writing the verdict? Can a redelivered event create a second run or overwrite a newer rejudge?

Do not let the worker inherit the API's trust

The API handles authentication and product rules. A judge worker handles hostile code. Keep their credentials, network paths, filesystem access, and process privileges separate. The worker should fetch only the source and tests needed for one job, run with narrowly scoped access, return structured results, and discard the workspace. The API should validate that the result belongs to the expected submission attempt before recording it.

Security tools are defense in depth. Docker's seccomp profile can restrict system calls, cgroups can account and constrain resource use, and filesystem/network/identity policy can reduce what the process can reach. Each control has limits; a kernel or runtime escape remains part of the threat model. For a public service, consider a stronger isolation approach and get the boundary reviewed before executing real untrusted submissions.
