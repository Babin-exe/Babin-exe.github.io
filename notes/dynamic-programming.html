Dynamic programming, without the magic words

The usual explanation starts with “overlapping subproblems” and “optimal substructure,” then leaves you staring at a blank editor. I find it easier to start with a recursive decision and ask which answers I keep calculating.

Dynamic programming (DP) is a way to solve a problem by reusing answers to smaller versions of the same problem. The name makes it sound more mysterious than it is. The core work is ordinary reasoning: define a small state, decide how it depends on earlier states, and make sure each state is computed only once.

Start with one concrete problem

You have unlimited coins with values {1, 3, 4}. What is the fewest number of coins that add up to amount 6? A naive approach tries every first coin:

  • take 1, then solve amount 5;
  • take 3, then solve amount 3;
  • take 4, then solve amount 2.

That gives a recursive definition. Let best(x) mean “the minimum coins needed to make amount x.” Once that sentence is precise, most of the solution is already visible.

Name the state so it contains exactly what the future needs

For this problem, one integer is enough: x, the remaining amount. The state does not need to remember the order in which we chose earlier coins because earlier choices do not change which coins are available next. That is an important modeling test: if two different histories lead to the same state, should they have the same future possibilities and answer? If yes, the state may be sufficient.

Start with a base case: best(0) = 0. Making amount zero needs no more coins. An amount below zero is impossible, so treat it as infinity when taking a minimum.

Turn the choice into a recurrence

If the first coin has value c, one coin is used and the remaining amount is x - c. Try each allowed coin and keep the best result:

best(0) = 0
best(x) = 1 + min(best(x - c)) for each coin c where c <= x

For amount six:

best(6) = 1 + min(best(5), best(3), best(2))
        = 1 + min(2, 1, 2)
        = 2  // use 3 + 3
dp = [0] + [infinity] * amount

for x in range(1, amount + 1):
    for coin in coins:
        if coin <= x:
            dp[x] = min(dp[x], dp[x - coin] + 1)

The loop order matches the dependency direction: before calculating dp[x], all smaller amounts are already known.

The savings come from remembering answers

Without reuse, a recursive solver expands the same remainder over and over. Memoization stores each answer the first time it is computed. Once best(2) has been solved, every later branch reads the stored value instead of expanding that sub-tree again.

Prune the Fibonacci call tree

fib(5) · same state, one answer
15 calls · 15 expanded

The tree repeats the same Fibonacci states down separate branches.

Memoization and tabulation are two evaluation orders

Top-down / memoizedBottom-up / tabulated
Write the recurrence recursively; cache each state.Choose an order that computes dependencies first.
Often computes only states reachable from the requested answer.Often makes memory and iteration order explicit.
Call-stack depth can become a limit.Can be easier to optimize to rolling memory.
Good while deriving or when many states are unreachable.Good when the full state range is manageable.

They are not different algorithms in spirit. Both evaluate the same recurrence and reuse each subproblem. The choice is mostly about clarity, reachable states, recursion depth, and memory.

Count states and transitions—not branches in the tree

There are amount + 1 states. For each amount, we try each of k coin values. That gives O(amount × k) time and O(amount) space. The uncached recursion can be exponential because the tree repeats work; the DP graph shares those repeated states.

For another problem, use this same accounting: how many distinct states can exist? How many choices/transitions do we inspect from each one? What does the stored answer cost? A recurrence can be correct and still too large if the state definition includes unnecessary detail.

A practical way to debug a DP

  1. Write one sentence for the state: “dp[x] means …”.
  2. List the decisions available from that state, including what information each decision changes.
  3. Write the recurrence in math or pseudocode before optimizing.
  4. Check the smallest/base cases by hand.
  5. Draw arrows from a state to the smaller states it needs; make sure the graph has a valid evaluation order.
  6. Compute a tiny example by hand and compare it to a table.
  7. Count unique states × work per state; then count stored values.
  8. Only after correctness, consider reducing memory or changing the recurrence.

When it is not DP

Recursion alone does not imply dynamic programming. If branches do not revisit the same state, memoization may add overhead without saving work. If the state forgets information that changes future options, caching it can produce a wrong answer.
