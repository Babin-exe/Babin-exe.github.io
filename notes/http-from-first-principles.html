HTTP, from the first byte to the page

A URL in the address bar looks like one action. Underneath it is a chain of smaller jobs: find the server, establish a connection, make a request, decide what the response means, then turn bytes into a page.

HTTP is the application-level conversation between a client and a server. It gives meaning to things like GET /articles, a response code, a header, or a body. It does not by itself decide how a hostname becomes an IP address, how packets find the machine, or how bytes are encrypted. Those jobs belong to surrounding layers.

This separation is useful because it keeps the mental model small. When a page fails, ask which job failed: name lookup, connection, TLS, routing, application logic, response interpretation, or rendering?

First, separate the layers

For https://notes.example.dev/posts/42?view=full, the browser parses the URL into scheme, host, port, path, and query. The host must be resolved to an address. The browser then creates a transport connection. For HTTP/1.1 or HTTP/2 over TCP, HTTPS adds a TLS handshake; HTTP/3 uses QUIC over UDP and integrates its security handshake with that transport.

An HTTP request has intent and context

In HTTP/1.1, a request is commonly written as a start line, header fields, a blank line, and an optional body. That visible text is a good teaching format; HTTP/2 and HTTP/3 do not send that exact text representation on the wire.

GET /posts/42?view=full HTTP/1.1
Host: notes.example.dev
Accept: text/html
Cookie: session=...

The method says what operation the client is asking for. The target identifies the resource or operation. Headers add context: acceptable response formats, authentication, caching conditions, content type, and more. A body often carries input for methods such as POST or PATCH, but the method's semantics—not the presence of a body—tell the server what that input means.

What happens between the request and the handler?

The request often hits an edge layer before application code: a CDN may serve a cached response, a reverse proxy may terminate TLS and route by host/path, and middleware may apply request-size limits, parse cookies, authenticate a session, or validate input. Only then does a route handler call the business logic and data store.

A response says both “what” and “how to interpret it”

A response contains a status code, header fields, and sometimes a body. 200 means the request succeeded in a general way; 201 commonly reports a created resource; 204 means success with no response content; 304 tells a cache that its stored representation is still valid. 400, 401, 403, and 404 describe different client-side or access outcomes. The exact code matters because browsers, proxies, and clients make decisions from it.

Headers carry metadata about the response representation and handling: Content-Type says what the body is, Cache-Control describes caching policy, Set-Cookie asks the browser to store a cookie, and ETag can identify a representation version. HTTP messages are not necessarily human-readable text; a body can be JSON, HTML, an image, a video stream, or binary data.

Methods make promises about effects

Two HTTP method properties are especially useful when designing an API:

  • Safe means the client is asking for a representation or status, not requesting a state change. GET is defined as safe. Logging the request is fine; turning a GET into “delete account” is not.
  • Idempotent means repeating the same request has the same intended effect on server state as making it once. The response may differ. PUT and DELETE are defined as idempotent; POST is not inherently idempotent.

This matters when a connection breaks at an awkward moment. The server may have completed a payment-like POST even though the client never received the response. Blindly retrying can create a duplicate. A client-generated idempotency key lets a server recognize a retry of the same logical operation and return the original result.

Caching: avoid repeating work when the representation is still fresh

Caching is not a shortcut bolted onto a URL; it is a protocol conversation. A response can state a freshness lifetime using Cache-Control. While that representation is fresh, a browser or intermediary can reuse it without contacting the origin. Later, the cache can ask if its copy is still current with a validator such as If-None-Match: "abc123". The server can answer 304 Not Modified, so the cache reuses its body.

For an application, the first useful question is “who can reuse this response?” A public product page may be reusable by a shared cache; a private profile response usually must not leak between users. Cache correctness depends on the representation and the headers that vary it, not just on whether the URL looks public.

The last leg happens in the browser

The response might be HTML that points to CSS, JavaScript, images, and fonts. The browser parses HTML into a DOM, parses CSS into style rules, computes layout, paints pixels, and executes scripts. Those scripts can request more resources, which starts more HTTP conversations. A “page load” is often a dependency graph, not one request.

CORS is a browser permission check, not an API login system

When JavaScript at one origin requests a different origin, the browser applies the same-origin policy. Cross-Origin Resource Sharing (CORS) is the server's way to tell the browser which origins may read the response. Some requests can be sent directly; a request using a non-safelisted method, header, or content type can trigger an OPTIONS preflight first. The browser sends the actual request only if the preflight response allows it.

CORS does not authenticate the user, and it does not stop a command-line client from calling an API. Authentication and authorization still belong on the server. CORS primarily controls what browser scripts are permitted to read.

This is the mental model I use when reading network logs: locate the earliest layer that could have answered the request, then follow the bytes until the browser can render them.
